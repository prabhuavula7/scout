# Roadmap

## Done

- Core pipeline: import (OpenAPI/Swagger URL or raw text), documentation crawling + chunking + embedding, understanding synthesis, grounded chat with citations.
- Local-first architecture: `packages/store`'s `LocalFileStore` persists everything under `~/.scout/runs/`, no database or server required for the default path.
- `scout` CLI: `understand`, `list`, `rm`, `chat`, `export`, `watch`, `refresh`, `generate`, `handoff`, `diff`, `research`, `serve`, `connectors`, `config`, `mcp`.
- Local web app (`scout serve`), bound to `127.0.0.1`, no login, reading the same run directories live. Not view-only: a persistent sidebar (Runs / New / Threads / Settings, collapsible to icon-only) and a "New" tab run the same `understand` pipeline as the CLI (fire-and-poll: the request returns immediately, the run's status page polls live), so a UI-only user never has to touch the terminal after the initial `npm install -g @dotapk7/scoutcli && scout serve`. Deleting a run (`scout rm`, or the trash icon on the Runs page) is available from both surfaces too.
- **Threads**: chat is no longer one conversation per run. `packages/store`'s `LocalFileStore` gained `ChatThreadRecord` + thread-scoped `appendChatMessage`/`getChatHistory`, with pre-threads `chat.jsonl` history lazily migrated into a synthesized "Main" thread on first read rather than a one-time migration script. A top-level Threads tab (`/threads`) lets you create/rename/delete threads, Claude/ChatGPT-style; the CLI (`scout chat <slug> --thread <name>`) and MCP (`ask_platform`'s `thread` param) gained the same scoping, defaulting to "Main" so nothing that predates this feature breaks.
- **Multi-run chat**: a thread can span more than one platform, on all three surfaces. `packages/store`'s new `MultiRunThreadStore` gives a multi-run thread its own home under `~/.scout/threads/<threadId>/` (a single-run thread still lives inside that run's own `LocalFileStore`, unchanged), so nothing about the existing single-run path had to change. `packages/agents`' `runAgenticChatAgent` now takes a `ChatPlatform[]` instead of one store/platformId (a single-run thread just passes a one-element array); `search_docs` merges and re-ranks results across every platform in scope and tags each `ChatSource` with which one it came from; `generate_starter_code`/`assemble_handoff` require an explicit `platform` slug when more than one platform is in scope, erroring with the valid slugs rather than guessing. The web Threads page flattened from "Runs → Threads → Chat" to a single thread list (with per-thread platform badges and a platform filter) plus a "new thread" picker for choosing one or several platforms. `scout chat` takes a comma-separated slug list (`scout chat stripe,hubspot --thread "sync"`) via a shared `resolveMultiThread` (title + platform-set match reuses a thread, otherwise creates one; there's no "Main"-style default for an arbitrary platform set, so a name is required). `ask_platform` gained `slugs`/`title` alongside the existing singular `slug`/`thread`, with the same create-or-reuse-by-title semantics. Verified live end-to-end on all three surfaces against a real Stripe + HubSpot thread: real OpenAI calls (browser, `scout chat`, and a real MCP stdio session against the built binary) all correctly merged and cited excerpts from both platforms' crawled docs in one answer, and reusing the same slugs + title (in either order) continued the same thread rather than creating a new one.
- **Thread-aware handoff**: `scout handoff`/`handoff_platform`/the web IDE-handoff section can fold a thread's conversation into the brief (`--thread`/`thread`/a thread dropdown) as an LLM-distilled "Already figured out in chat" section, one extra `LLMProvider.complete` call over the thread's transcript (`summarizeThreadForHandoff`), not the raw transcript pasted in. An empty or purely exploratory thread yields no section, not a padded-out one. Verified live against a real Stripe payouts conversation: the distilled summary correctly surfaced the specific `Stripe-Account` header requirement, the real Account Links onboarding endpoint, and the open decision point the conversation left unresolved.
- **Collapsible, resizable web UI**: the sidebar collapses to icon-only (state persisted, every page's own content width grows to use the reclaimed space); the Threads page's Runs↔Threads and Threads↔Chat panes are independently draggable and persisted per-column.
- Connectors as JSON config (`packages/connectors/registry/*.json` + `~/.scout/connectors/` overrides), not code.
- `scout watch`: polls doc URLs, hashes content, re-runs documentation + understanding agents on change, archives the previous snapshot to `history/`.
- `scout research`: related articles/tutorials/use cases via a configured search provider, surfaced in the viewer and `scout export`.
- **Provider-agnostic LLM + search**: `packages/ai` implements OpenAI, Anthropic, Azure OpenAI, OpenRouter, and a generic OpenAI-compatible adapter (covers local/open-source models via Ollama, LM Studio, vLLM, etc); `packages/agents/src/search` implements Tavily and SerpApi. Multiple entries can be configured per role (chat/embedding for LLMs) with priority-ordered automatic fallback. Config is shared between the CLI (`scout config llm`/`scout config search`) and a Settings tab in the web viewer, both reading/writing the same `~/.scout/config.json`; a pre-existing single-key config or `OPENAI_API_KEY`/`TAVILY_API_KEY` env vars migrate/fall back automatically.
- `scout mcp`: MCP server with full CLI/web parity, 11 tools (`understand_platform`, `ask_platform`, `list_platforms`, `list_connectors`, `refresh_platform`, `diff_platform`, `generate_platform`, `handoff_platform`, `export_platform`, `research_platform`, `remove_platform`) for Claude Code, Codex, Gemini CLI, and other MCP-speaking agents. Verified end-to-end over the real stdio protocol against the published package, and live against Claude Code and Claude Desktop.
- Dormant hosted mode (`apps/api` + `apps/workers`, Fastify + Clerk + Postgres/pgvector + BullMQ/Redis) kept working but excluded from the default build/dev/test pipeline, for anyone who wants a multi-user hosted deployment later.
- **npm-publish readiness**: `packages/cli` bundles the connector registry JSON and a prebuilt `apps/web` viewer (`.next` output, minus webpack's build cache and Next's own trace files) inside `dist/`, with `next`/`react`/`react-dom` as real dependencies rather than pnpm workspace links, so `scout serve` runs the same way from a real `npm install -g @dotapk7/scoutcli` as it does in the monorepo. Verified with a real `npm pack` + global install into an isolated prefix, outside the monorepo: `connectors list`, `scout serve`, and the viewer's HTTP response all work. Published to npm as `@dotapk7/scoutcli` (the unscoped `scoutcli` was rejected by npm's name-similarity policy against an existing `scout-cli` package); the `scout` command name is unaffected. Verified again post-publish with a real `npm install -g @dotapk7/scoutcli` from the registry, outside the monorepo.
- **Failure reasons surfaced in the web UI**: a failed run used to show only a red "Failed" badge with no way to see why short of the CLI's stderr or `agent-runs.jsonl`. `GET /api/runs/[slug]` now returns the most recent failure's error message (`lastError`), rendered as a banner on the run's page.
- **Thin/JS-rendered doc page detection**: `packages/agents/src/documentation-agent.ts` flags any crawled page whose extracted markdown comes back under ~500 characters (a heuristic for "this is a JS-rendered SPA shell cheerio's static fetch can't execute," the most common real cause). Surfaced as an amber warning banner on the run's page (`platform.docsCrawlWarning`), not a silent thin answer.
- **Pre-run crawl size estimate**: `scout understand` prints a one-line estimate (seed URL count, known byte/token size, crawl depth/page cap) before starting; the web "New" form has an on-demand "Preview crawl size estimate" button hitting the same `estimateCrawlCost` helper (`packages/agents/src/crawl-estimate.ts`). Deliberately doesn't attempt a $ figure (provider/model pricing isn't tracked and would go stale); states token/byte counts only and defers cost to "depends on your provider's pricing."
- **Recursive documentation crawling**: `runDocumentationAgent` now optionally follows same-origin links found on each crawled page, breadth-first, up to `--docs-depth` hops (default 1) and hard-capped at `--docs-max-pages` (default 20) regardless of depth, so a crawl can't spider an entire site unbounded. `--docs-depth 0` reproduces the old fixed-set-only behavior exactly.
- **Disclosed understanding scope**: endpoint summaries and doc chunks feeding synthesis are capped (300 / 100, up from silent caps of 150 / 40) to bound prompt size/cost; doc-chunk selection now samples evenly across every crawled source page (`getRepresentativeDocChunks`) instead of just the most-recently-crawled pages, and a run's page discloses via an amber banner whenever a cap was actually hit, instead of silently looking complete.
- **Web UI parity with the CLI**: a research trigger on the Understanding page (same pipeline as `scout research`), chat/research error handling that surfaces the real failure reason instead of an unhandled 500, and custom error/404 pages instead of Next.js's defaults.
- **Docker support**: `Dockerfile` + `docker-compose.yml`, `docker compose up` to run Scout with no Node/pnpm install at all. Built and run for real during development (not just written): caught and fixed a dangling `.env.local` symlink breaking the build, an `npm install` incompatibility with `workspace:*` devDependencies, and a missing `scout` binary on `PATH` inside the container. Verified end-to-end: real `scout understand` run via `docker exec`, reachable through the mapped port, surviving a container restart via the named volume.
- **Automated web UI test coverage**: 46 tests across API route handlers and interactive components (sidebar, Runs list, New-run form, chat, Understanding page, Settings), closing the gap this list used to flag; `apps/web` now has real automated coverage alongside `packages/store`/`packages/cli`/`packages/connectors`/`packages/agents`.
- **MCP client compatibility verified**: the stdio JSON-RPC protocol handshake (`initialize`/`tools/list`/`tools/call`) tested directly, plus a real Claude Code client connection. Setup snippets for Claude Code, Claude Desktop, Cursor, and Codex CLI added to the README.
- **Fresh screenshots**: the old web-app UI's screenshots (pre-CLI-pivot) removed from `public/`; replaced with 7 new ones captured against the current interface (Runs, New, Understanding with its table of contents, entity diagram, API Explorer, AI Chat, Settings) and embedded in the README.
- **`@dotapk7/scoutcli` on npm**: the unscoped `scoutcli` name was rejected by npm's anti-typosquatting policy against an existing `scout-cli` package; published and verified under the scoped name instead (`scout` command name unaffected). Multiple versions shipped and verified with real global installs + registry checks, not just `npm pack --dry-run`.
- **First-run onboarding**: a dismiss-when-configured banner on the web app's Runs/New pages when no LLM provider is set up yet, an explicit empty state on Settings' provider list, and concrete copy-paste provider-setup commands in `scout config llm/search list`'s empty output and the "not configured" errors thrown mid-pipeline.
- **Staged pipeline progress UI**: the Understanding page shows which step (import → crawl docs → understand & synthesize) a run is actually on, with rotating status phrases, instead of an indistinguishable "not generated yet" empty state while a run is in progress.
- **`scout refresh <slug>` / refresh button**: regenerates a run's understanding without re-importing the spec (`--recrawl` also re-fetches doc URLs). Confirmed multiple runs can import/crawl/synthesize concurrently (safe by construction, no shared queue/lock). Understanding-synthesis scope raised (endpoint summaries 300→750, doc chunks 100→200) with matching crawl-default increases.
- **`scout generate <slug> --lang ts|py`**: generates a runnable starter script (auth handshake + one real read call) directly from a run's blueprint. Real templates for API-key-header, Bearer-token, and API-key-query auth; anything else (OAuth2, no endpoints, write-only endpoints) produces an honest stub, never fabricated-looking code. Generated code is syntax-checked (`node --check`/`python3 -m py_compile`) before being returned, and a matching `.env.example` is scaffolded alongside it. `--list-workflows` and `--out <path>` round out the CLI; a "Starter code" section on the web Understanding page and a `generate_platform` MCP tool share the exact same underlying function.
- **`scout diff <slug>`**: drift detection between a run's current and previously-refreshed understanding (narrative sections changed, workflows/data-model entities/pitfalls/integration opportunities added or removed), reusing the snapshot Scout already took before every refresh, no new storage. Also a `diff_platform` MCP tool.
- **Fixed a real auth-fabrication bug**: the web Explorer page's per-endpoint code snippets used to hardcode `Authorization: Bearer $API_TOKEN` regardless of a run's actual detected auth scheme. Confirmed live against the real Stripe demo run (whose actual scheme is `basic`, not Bearer) and fixed to reflect the real scheme, or an honest "no safe default" comment, instead.
- **`scout handoff <slug> --lang ts|py`**: assembles a paste-ready Markdown brief for a coding agent (Claude Code, Cursor, etc.): task/workflow steps, the auth handshake, the exact same starter script `scout generate` produces (same stub/syntax-validation honesty guarantees, no duplicated codegen logic), its `.env.example`, the exact endpoint used, and the pitfalls/security observations/gaps Scout's synthesis flagged, so a coding agent isn't starting from a blank page or re-deriving what Scout already verified. Free-text spec/LLM-derived content is sanitized against markdown fence-break injection (a run of 3+ backticks can't close the doc's code fence early and inject content past it, since this brief is meant to be pasted directly into an agent as its task prompt). An "IDE handoff" section on the web Understanding page (copy-to-clipboard) and a `handoff_platform` MCP tool share the same underlying function; `scout handoff --copy` gives the CLI the same one-step clipboard copy (shells out to `pbcopy`/`clip`/`wl-copy`/`xclip`/`xsel`, whichever the platform actually has, and falls back to printing with a clear error if none are found, rather than a silent failure). Verified against real stored runs: an honest stub for Stripe (`basic` auth, unsupported in v1) and GitHub (`none`), and a real syntax-validated script for HubSpot (`api_key_query`), plus a real `pbcopy` run on this machine confirming the clipboard actually receives the brief.
- **User-uploaded documents and attached links**: `scout docs add <slug> <file-or-url>` (an `attach_document_platform` MCP tool, and an "Attach a document" control on the web app's Understanding page) ingests a local file or an http(s) link through the same chunk/embed pipeline the documentation crawler uses (`chunkDocument`/`embedAndStoreChunks`), tagged `origin: "upload"`/`"link"` in `DocChunkMetadata` instead of `"crawl"`. `officeparser` handles PDF, docx/xlsx/pptx, odt/odp/ods, rtf, csv, md, and html; plain txt/json/yaml are read directly. 10 MB per item; zip archives out of scope. Google Drive links are refused with a clear explanation rather than silently ingesting a viewer page's HTML chrome. `store.listDocSources`/`deleteDocChunksBySource` (both derived from the existing `chunks.json`, no new storage) back `scout docs list`/`scout docs rm` and a delete button in the web UI. The chat UI only renders a citation as a clickable link when its source is a real http(s) URL, so an uploaded file's synthetic `scout-upload://` reference shows as a plain badge instead of a dead link.
- **Agentic chat**: `scout chat`/`ask_platform`/the web chat page now run a real multi-turn tool-calling loop instead of single-shot RAG. `packages/ai`'s `LLMProvider` gained `completeWithTools` (native Anthropic tool-use; one shared implementation for the OpenAI-wire function-calling shape used by OpenAI, Azure OpenAI, and every OpenAI-compatible endpoint), and a new agent (`runAgenticChatAgent`) registers four tools the model can call mid-conversation: `search_docs` (the existing hybridSearch), `web_search` (the existing Tavily/SerpApi providers, only offered when one is configured), `generate_starter_code`, and `assemble_handoff` (the exact same functions `scout generate`/`scout handoff` use). Every returned source is tagged with real provenance: `docs` (real cosine score), `web` (URL), or `model_knowledge` (the model answered without calling any tool this turn -- flagged unverified, never given a fabricated confidence number). If a configured provider's tool-calling fails outright on the first turn, this degrades to the old single-shot grounded RAG behavior (`runChatAgent`, kept as-is) rather than hard-failing the chat. Verified with a real live OpenAI run against the HubSpot demo run: the model called `search_docs` for real, returned 7 real doc citations, and caught a genuine discrepancy between the stored blueprint's auth scheme and what the live docs actually say.

## Not yet implemented

- **More connectors**: 18 are declared in `packages/connectors/registry/`, only Contentful and Bynder have been run end-to-end. Adding one is now a JSON-only PR; see `CONTRIBUTING.md`. Verifying one requires a human to actually compare the output against the platform's real docs, so this isn't something to batch-automate; left as ongoing/contributor work.
- **More import kinds**: GraphQL introspection, GitHub repo spec discovery, Postman collections, HAR files. `packages/agents/import-agent.ts` only handles OpenAPI/Swagger URL and raw text today.
- **Local vector search upgrade path**: `packages/store`'s hybrid search is brute-force in-memory cosine similarity + keyword blend, fine at CLI/single-platform scale. `sqlite-vec` is a documented drop-in if chunk counts get large.
- **No published Docker image**: `docker compose up` always builds locally (`build: .`); there's no image on Docker Hub/GHCR yet for a pull-and-run without a local build.

## Suggested build order for contributors

1. Pick an unimplemented connector from `packages/connectors/registry/`, run `scout understand` against its real spec + docs, and flip `implemented` to `true` once it works cleanly.
2. Add a new import kind to `packages/agents/import-agent.ts` (Postman collections are probably the easiest next one, same endpoint-shape output).
3. Expand `scout generate`'s v1 auth-scheme taxonomy (currently API-key-header, Bearer-token, API-key-query) or add write-call support with a defined placeholder-value convention, without compromising the honest-stub-over-fabrication stance the rest of the feature is built on. `scout handoff` embeds `generate`'s output directly, so this expands both at once.
